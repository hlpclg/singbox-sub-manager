# v0.7 备份、升级与回滚 — 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: 使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 按 Task 逐个实施。每个 Task 遵循 `docs/agent-workflows/task-lifecycle.md` 的执行顺序：契约确认 → 验收矩阵 → 最小实施 → 聚焦测试 → 规格符合性审查 → 代码质量审查 → Task 专项门禁 → 计划与用户文档更新 → 主提交 → 状态封账提交 → 下一 Task。

**依据设计**：`docs/superpowers/specs/2026-08-17-v0.7-backup-upgrade-rollback-design.md`（已批准）。本计划只描述契约、不变量、验收测试和验证命令，不提供生产实现代码。

**Global Constraints（优先于各 Task，Task 不得覆盖）**

- 不修改 v0.4/v0.5/v0.6 已稳定的 health check ID、JSON schema 或 `proxyctl health`/`monitor`/`node` 现有行为。
- 不引入远程备份、加密归档、定时备份 systemd timer、`proxyctl uninstall`；这些是设计文档明确的非目标。
- 备份/恢复涉及的原子写入必须遵循仓库既有模式：同目录临时文件 + `fsync` + 原子 `rename` + 父目录 `fsync`；文件权限保持不低于原文件权限，敏感文件（token、sing-box/Caddy 配置、monitor 状态）不得放宽到超过 `0600`。
- 涉及 I/O、进程执行、取消或超时的路径必须覆盖成功、失败、取消、超时和持久化五类场景；不适用须在验收矩阵中写明原因。
- Go 命令必须在 Go 1.22 容器执行（本机 `go` 不在 PATH）。
- 恢复/升级/回滚逻辑涉及并发（与 `monitor` 的 `FileLock` 交互）时，须由具备并发推理能力的实现者负责并接受独立审查。
- 每个 Task 独立提交，未通过规格符合性和代码质量审查不得进入下一 Task。

## Task 1: 备份打包（internal/backup 归档与清单）

**Files:**
- Create: `internal/backup/archive.go`, `internal/backup/archive_test.go`
- Create: `internal/backup/manifest.go`, `internal/backup/manifest_test.go`

**契约：**

- `Create(ctx context.Context, opts CreateOptions) (Manifest, error)`：按设计文档第 4 节的固定路径集合打包为 `.tar.gz`，路径存在才打包，不存在记入 `manifest.Skipped`。
- `Manifest{SchemaVersion int, CreatedAt time.Time, ProxyctlVersion string, Files []FileEntry, Skipped []string}`，`FileEntry{Path, SHA256, Mode}`。
- `CreateOptions` 至少包含目标目录、`--out` 覆盖路径、当前 `proxyctl` 版本注入（用于测试可控）、时钟注入（`Now func() time.Time`）。
- 归档写入采用同目录临时文件 + `fsync` + 原子 `rename`；失败时不得残留可被误认成功归档的最终文件名。

**不变量：**

- 归档内每个文件的 SHA-256 与打包时读取内容一致（写入清单前读、写入归档前不得被修改，或采用读取一次后同时用于内容和摘要）。
- 缺失路径不导致整体失败，只进入 `Skipped`。
- 归档文件名冲突（同一秒内多次调用）不得互相覆盖或产生半成品文件。

## Task 2: 恢复与校验（internal/backup 恢复路径）

**Files:**
- Create: `internal/backup/restore.go`, `internal/backup/restore_test.go`

**契约：**

- `Verify(archivePath string) (Manifest, error)`：解包清单、重新计算每个文件 SHA-256 并与清单比对，`schema_version` 不支持时返回明确错误。
- `Restore(ctx context.Context, archivePath string, opts RestoreOptions) (Result, error)`：`RestoreOptions{DryRun bool}`。`DryRun=true` 时只返回将变更的路径列表和新旧摘要对比，不写入文件系统。
- `Result{Restored []string, Failed []string}`：非 dry-run 时，即使部分文件写入失败也要返回已完成和未完成的集合，不得因为一个文件失败而丢失已成功文件的记录。
- 恢复不在本模块内触发服务重启；重启编排属于 Task 3 的 CLI 层职责，`internal/backup` 只负责文件级别的读写和校验。

**不变量：**

- 校验和不匹配时，`Verify`/`Restore` 拒绝执行且不写入任何文件。
- 逐文件原子写入（临时文件 + rename），单个文件失败不影响其余文件已完成的写入，也不重复回退已成功的文件（回退属于 Task 3 编排职责，见设计文档第 5 节）。
- `DryRun` 模式下文件系统零写入，可通过测试注入的只读文件系统或写入计数器验证。

### 验收矩阵

| 需求或不变量 | 主要风险 | 成功路径 | 失败路径 | 取消/超时 | 持久化/清理 | 确定性测试 | 验证命令 | 证据 |
|---|---|---|---|---|---|---|---|---|
| 校验和不匹配拒绝执行 | 损坏或被篡改归档被静默恢复 | 校验和一致时 `Verify` 通过 | 任一文件校验和不匹配时 `Restore` 返回错误且零写入 | 不适用 | 不适用 | `TestRestore_ChecksumMismatchRejected` | `go test ./internal/backup -run Restore -v` | 待执行 |
| DryRun 零写入 | dry-run 意外落盘造成用户误判 | 返回准确的变更预览列表 | 不适用 | 不适用 | 文件系统在调用前后字节级一致 | `TestRestore_DryRunNoWrites` | 同上 | 待执行 |
| 部分失败时准确报告 Restored/Failed | 静默声称整体成功掩盖恢复失败 | 全部成功时 `Failed` 为空 | 中途某文件写入失败时，之前已成功文件仍在 `Restored`，该文件及之后未处理文件在 `Failed` | ctx 取消时已完成写入保留在 `Restored`，未处理路径归入 `Failed` 并附带取消原因 | 恢复failed路径的原文件保持不变（未被半写覆盖） | `TestRestore_PartialFailureReporting`、`TestRestore_Cancellation` | 同上 | 待执行 |

## Task 3: CLI 命令与保留策略（cmd/proxyctl backup.go）

**Files:**
- Create: `cmd/proxyctl/backup.go`, `cmd/proxyctl/backup_test.go`
- Modify: `cmd/proxyctl/main.go`（注册子命令）

**契约：**

- `proxyctl backup [--out <path>] [--keep <n>]`：调用 Task 1 的 `Create`，成功且未指定 `--out` 时按创建时间清理 `backups/` 目录中超出 `--keep`（默认 10，`0` 不清理）的最旧归档。
- `proxyctl restore <archive-path> [--dry-run] [--no-restart]`：调用 Task 2 的 `Restore`；非 dry-run 且未传 `--no-restart` 时，对归档 `manifest.Files` 中命中 `sing-box`/`caddy` 路径的服务执行重启并复用 v0.6 已有的复检语义（成功清零、失败保留告警），复检失败则用恢复前状态回滚本次 restore 涉及的文件。
- `proxyctl backup list`：读取 `backups/` 目录，输出归档文件名、时间戳、大小、`manifest.ProxyctlVersion`，按时间倒序。
- 退出码延续仓库既有约定：`0` 成功；非 0 区分参数错误、校验失败、部分失败（含"已恢复文件但复检/重启失败并已回滚"和"回滚本身失败，需人工介入"两种更严重的情形，须在错误信息中明确区分）。

**不变量：**

- 保留策略清理只删除自身创建的、路径匹配归档命名规则的文件，不删除用户放入 `backups/` 目录的其他文件。
- restart-then-recheck 使用与 `internal/monitor` 相同的服务控制器抽象（避免重复实现 `systemctl restart` 调用），但不与 monitor 共享运行时状态或触发 monitor 的失败计数。
- restore 引发的回滚是尽力而为：若回滚本身失败，命令必须以最高严重级别的退出码返回，并清楚列出哪些路径处于不确定状态，不得掩盖为普通失败。

### 验收矩阵

| 需求或不变量 | 主要风险 | 成功路径 | 失败路径 | 取消/超时 | 持久化/清理 | 确定性测试 | 验证命令 | 证据 |
|---|---|---|---|---|---|---|---|---|
| `--keep` 保留策略正确清理 | 误删用户文件或保留数量错误 | 超出 `--keep` 的最旧归档被清理，最近 N 份保留 | 清理阶段单个文件删除失败不影响备份本身已成功 | 不适用 | `--keep 0` 不清理；非自身命名文件不受影响 | `TestBackupCmd_RetentionPrunesOldest`、`TestBackupCmd_KeepZeroDisablesPrune` | `go test ./cmd/proxyctl -run Backup -v` | 待执行 |
| restore 触发重启并复检 | 恢复配置后服务未生效，用户误判恢复成功 | 命中 sing-box/caddy 路径时重启并复检通过 | 复检失败时回滚本次 restore 并返回非 0 退出码 | 重启/复检超时按 v0.6 既有超时语义处理 | 回滚失败时返回最高严重级别退出码并列出不确定路径 | `TestRestoreCmd_RestartRecheckSuccess`、`TestRestoreCmd_RecheckFailureRollsBack`、`TestRestoreCmd_RollbackFailureReported` | `go test ./cmd/proxyctl -run Restore -v` | 待执行 |
| `--no-restart` 跳过重启 | 用户预期不重启但命令仍重启，造成非预期服务中断 | 传入时只落盘，不调用重启 | 不适用 | 不适用 | 不适用 | `TestRestoreCmd_NoRestartSkipsServiceControl` | 同上 | 待执行 |
| `backup list` 输出准确 | 列表与实际归档不符导致误选恢复目标 | 按时间倒序列出全部有效归档及版本号 | 目录中存在无法解析的文件时跳过并不中止整体列出 | 不适用 | 不适用 | `TestBackupListCmd_OrdersByTime` | `go test ./cmd/proxyctl -run BackupList -v` | 待执行 |

## Task 4: install-proxy.sh update/rollback

**Files:**
- Modify: `install-proxy.sh`
- Modify/Create: `tests/test_install_update.sh`

**契约：**

- `sudo ./install-proxy.sh update`：
  1. 查询 GitHub Release 最新 tag（复用现有版本查询模式）。
  2. 调用 `proxyctl backup` 生成升级前快照，记录快照文件路径（本次 update 专用，不依赖用户此前已有快照）。
  3. 下载对应架构的 `proxyctl-linux-{amd64,arm64}`，用 Release 附带 `checksums.txt` 校验 SHA-256。
  4. 校验通过后原子替换本机 `proxyctl` 二进制（临时文件 + `chmod` + `rename`）。
  5. 执行既有健康检查；失败则用步骤 2 的快照执行等价于 `rollback --to <快照>` 的流程并以非 0 退出。
- `sudo ./install-proxy.sh rollback [--to <backup-id>]`：不带参数时使用最近一次由本机 `update`/`rollback` 记录的快照；带参数时使用指定归档路径或 ID；找不到可用快照时明确报错，不做静默无操作。
- 下载失败、校验失败必须在替换二进制之前发现；已下载的临时文件校验失败时删除并保留原二进制不变。

**不变量：**

- 二进制替换前，原 `proxyctl` 必须仍可用（不得先删除旧二进制再下载新的）。
- `update` 自动回滚只使用本次 update 创建的快照 ID，不得选择任意历史快照。
- 回滚路径复用 Task 3 的 `proxyctl restore`，不重新实现文件恢复逻辑。

### 验收矩阵

| 需求或不变量 | 主要风险 | 成功路径 | 失败路径 | 取消/超时 | 持久化/清理 | 确定性测试 | 验证命令 | 证据 |
|---|---|---|---|---|---|---|---|---|
| 校验失败不替换二进制 | 损坏/篡改的下载文件被安装并导致服务不可用 | checksum 匹配时替换成功 | checksum 不匹配时保留原二进制，脚本以非 0 退出 | 下载超时视为失败路径，不替换 | 临时下载文件清理，不残留 | `test_install_update_checksum_mismatch` | `bash tests/test_install_update.sh` | 待执行 |
| 健康检查失败自动回滚到本次快照 | 升级引入回归后无人值守环境持续故障 | 健康检查通过时保留新二进制 | 健康检查失败时回滚到 update 自建快照并复检通过 | 不适用（复检超时按既有健康检查语义处理） | 回滚使用 Task 3 `proxyctl restore`，不重复实现 | `test_install_update_healthcheck_failure_rolls_back` | 同上 | 待执行 |
| `rollback` 找不到快照时明确报错 | 静默无操作让用户误以为已回滚 | 存在快照时按指定或最近快照回滚 | 无可用快照时非 0 退出并给出明确提示 | 不适用 | 不适用 | `test_install_rollback_no_snapshot_errors` | 同上 | 待执行 |

**README：** 本 Task 改变运维命令，`README.md` 必须在主提交中同步 `update`/`rollback` 使用说明和失败自动回滚行为。Shell 文件变化后执行 `shellcheck install-proxy.sh`。
