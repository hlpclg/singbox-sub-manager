## Task 1: 备份打包（internal/backup 归档与清单）

**Files:**
- Create: `internal/backup/archive.go`, `internal/backup/archive_test.go`
- Create: `internal/backup/manifest.go`, `internal/backup/manifest_test.go`

**契约：**

- `Create(ctx context.Context, opts CreateOptions) (Manifest, error)`：按设计文档第 4 节的固定路径集合打包为 `.tar.gz`，路径存在才打包，不存在记入 `manifest.Skipped`。
- `Manifest{SchemaVersion int, CreatedAt time.Time, ProxyctlVersion string, Files []FileEntry, Skipped []string}`，`FileEntry{Path, SHA256, Mode}`。
- `CreateOptions` 至少包含目标目录、`--out` 覆盖路径、当前 `proxyctl` 版本注入（用于测试可控）、时钟注入（`Now func() time.Time`）。
- 归档写入采用同目录临时文件 + `fsync` + 原子 `rename`；失败时不得残留可被误认成功归档的最终文件名。

**不变量：**

- 归档内每个文件的 SHA-256 与打包时读取内容一致（写入清单前读、写入归档前不得被修改，或采用读取一次后同时用于内容和摘要）。
- 缺失路径不导致整体失败，只进入 `Skipped`。
- 归档文件名冲突（同一秒内多次调用）不得互相覆盖或产生半成品文件。
- 默认备份目录（`/var/lib/singbox-sub-manager/backups`）创建时权限为 `0700`；归档文件权限为 `0600`；`Create` 不得依赖调用方 umask 达到该权限，必须显式设置。归档内单个文件条目的 tar header 权限沿用原文件 `Mode`，且不得高于 `0600`（token、sing-box/Caddy 配置、monitor 状态均以 `0600` 落盘）。

## Task 2: 恢复与校验（internal/backup 恢复路径）

**Files:**
- Create: `internal/backup/restore.go`, `internal/backup/restore_test.go`
- Create: `internal/backup/lock.go`, `internal/backup/lock_test.go`（有界重试锁协调包装）

**契约：**

- `Verify(ctx context.Context, archivePath string) (Manifest, error)`：解包清单、重新计算每个文件 SHA-256 并与清单比对，`schema_version` 不支持时返回明确错误；接受 `ctx` 以覆盖大归档校验的取消/超时。
- **提取安全边界（先于任何写入执行的预检，属于 `Verify` 的一部分或 `Restore` 写入前的强制前置步骤）：**
  - 拒绝清单或 tar 条目中的绝对路径、包含 `..` 的路径穿越、重复路径条目。
  - 拒绝 tar 中的符号链接、硬链接、设备文件等非普通文件/目录条目。
  - 拒绝"清单与 tar 实际内容不一致"的归档：tar 中存在清单未声明的条目，或清单声明的条目在 tar 中缺失，均视为校验失败。
  - 以上任一条件触发时，返回明确的分类错误（区分"路径不安全"与"内容不一致"），且不得有任何文件系统写入（含临时文件）。
- `Restore(ctx context.Context, archivePath string, opts RestoreOptions) (Result, error)`：
  - `RestoreOptions{DryRun bool, DestRoot string, Lock Locker}`。`DestRoot` 为目标根目录注入点（生产默认 `/`，测试注入临时目录），归档内路径均相对 `DestRoot` 解析，不得依赖进程当前工作目录。
  - `Locker` 接口为 `TryLock() error` / `Unlock() error`（由调用方传入满足该接口的实现，`internal/backup` 不导入 `internal/monitor`，避免循环依赖；Task 3 负责用 `monitor.FileLock` 适配注入）。`Restore` 在写入前必须持有锁；`Locker` 为 `nil` 时视为调用方明确放弃锁协调（仅限测试或未来单机以外场景使用），生产 CLI 路径必须传入。
  - `DryRun=true` 时只计算并返回预览，不获取锁、不写入文件系统。
- `Result{Restored []string, Failed []string, Preview []FileDiff}`：`FileDiff{Path string, Action string /* create|overwrite|unchanged */, OldSHA256, NewSHA256 string}`。非 dry-run 时 `Preview` 为空，`Restored`/`Failed` 按写入结果填充；dry-run 时 `Restored`/`Failed` 为空，`Preview` 给出新旧摘要对比。
- 恢复不在本模块内触发服务重启；重启编排属于 Task 3 的 CLI 层职责，`internal/backup` 只负责文件级别的读写、校验和锁协调。

**锁协调契约（`internal/backup/lock.go`）：**

- 提供 `AcquireWithRetry(ctx context.Context, l Locker, interval time.Duration, maxWait time.Duration) error`：对不支持阻塞等待的 `TryLock`（如 `monitor.FileLock`）做有界轮询封装，不修改 `internal/monitor/lock.go`。
- 超过 `maxWait` 仍未获取锁时返回可识别的"锁繁忙"错误（区别于其他内部错误）；`ctx` 取消时立即返回 `ctx.Err()`，不再继续轮询。
- 成功获取后，`Restore` 必须在所有退出路径（成功、失败、panic 恢复、ctx 取消）上调用 `Unlock`；测试须验证锁在异常路径下也被释放，不遗留持锁进程。

**不变量：**

- 校验和不匹配、路径不安全或清单与内容不一致时，`Verify`/`Restore` 拒绝执行且不写入任何文件（含不获取锁）。
- 逐文件原子写入（临时文件 + rename），单个文件失败不影响其余文件已完成的写入，也不重复回退已成功的文件（回退属于 Task 3 编排职责，见设计文档第 5 节）。
- `DryRun` 模式下文件系统零写入、零加锁，可通过测试注入的只读文件系统或写入/加锁计数器验证。
- 所有写入路径基于 `DestRoot` 解析后仍须落在 `DestRoot` 内（提取安全边界的第二重防御，即使清单校验已拒绝穿越路径）。

|---|---|---|---|---|---|---|---|---|

## Task 3: CLI 命令与保留策略（cmd/proxyctl backup.go）

**Files:**
- Create: `cmd/proxyctl/backup.go`, `cmd/proxyctl/backup_test.go`
- Modify: `cmd/proxyctl/main.go`（注册子命令）

**契约：**

- `proxyctl backup [--out <path>] [--keep <n>]`：调用 Task 1 的 `Create`，成功且未指定 `--out` 时按创建时间清理 `backups/` 目录中超出 `--keep`（默认 10，`0` 不清理）的最旧归档。
- `proxyctl restore <archive-path> [--dry-run] [--no-restart]`：调用 Task 2 的 `Restore`，生产路径传入 `DestRoot="/"`、`Lock=monitor.NewFileLock("/run/lock/singbox-sub-manager-monitor.lock")`（复用 v0.6 既有锁文件路径以保证与 `monitor` 互斥，通过 Task 2 的 `AcquireWithRetry` 封装，不直接调用 `TryLock`）。非 dry-run 且未传 `--no-restart` 时，对归档 `manifest.Files` 中命中 `sing-box`/`caddy` 路径的服务执行重启并复用 v0.6 已有的复检语义（成功清零、失败保留告警），复检失败则用恢复前状态回滚本次 restore 涉及的文件。锁繁忙（`AcquireWithRetry` 超时）时返回明确提示"monitor 正在运行，请稍后重试或先 `proxyctl monitor pause`"，不静默重试到无限等待。
- `proxyctl backup list`：读取 `backups/` 目录，输出归档文件名、时间戳、大小、`manifest.ProxyctlVersion`，按时间倒序。
- 退出码延续仓库既有约定：`0` 成功；非 0 区分参数错误、校验失败、部分失败（含"已恢复文件但复检/重启失败并已回滚"和"回滚本身失败，需人工介入"两种更严重的情形，须在错误信息中明确区分）。

**不变量：**

- 保留策略清理只删除自身创建的、路径匹配归档命名规则的文件，不删除用户放入 `backups/` 目录的其他文件。
- restart-then-recheck 使用与 `internal/monitor` 相同的服务控制器抽象（避免重复实现 `systemctl restart` 调用），但不与 monitor 共享运行时状态或触发 monitor 的失败计数。
- restore 引发的回滚是尽力而为：若回滚本身失败，命令必须以最高严重级别的退出码返回，并清楚列出哪些路径处于不确定状态，不得掩盖为普通失败。

## Task 4: install-proxy.sh update/rollback

**Files:**
- Modify: `install-proxy.sh`
- Modify/Create: `tests/test_install_update.sh`

**契约：**

- `sudo ./install-proxy.sh update`：
  1. 查询 GitHub Release 最新 tag（复用现有版本查询模式）。
  2. 调用 `proxyctl backup` 生成升级前配置快照，记录快照文件路径（本次 update 专用，不依赖用户此前已有快照）。
  3. **暂存当前 `proxyctl` 二进制**：将现有二进制复制（非移动）到升级会话专属目录（如 `/var/lib/singbox-sub-manager/updates/<timestamp>/proxyctl.previous`），并记录其自身 SHA-256，作为二进制回滚的唯一可信来源；原二进制此时保持原路径不变、可继续执行。
  4. 下载对应架构的 `proxyctl-linux-{amd64,arm64}`，用 Release 附带 `checksums.txt` 校验 SHA-256。
  5. 校验通过后原子替换本机 `proxyctl` 二进制（临时文件 + `chmod` + `rename`）。
  6. 执行既有健康检查；**失败则先原子恢复步骤 3 暂存的旧二进制（临时文件 + rename，校验暂存文件 SHA-256 与记录一致后才恢复），再用步骤 2 的快照执行等价于 `rollback --to <快照>` 的配置回滚流程**，两者均完成后以非 0 退出。
  7. 健康检查通过后清理步骤 3 的暂存二进制和会话目录；清理失败只记录警告，不影响 `update` 本身的成功状态。
- `sudo ./install-proxy.sh rollback [--to <backup-id>]`：
  - 回滚范围明确覆盖**二进制和配置两部分**：使用指定或最近一次 `update` 会话记录的暂存二进制（步骤 3 产物）恢复 `proxyctl`，并用对应配置快照执行等价于 `proxyctl restore` 的配置回滚。
  - 不带参数时使用最近一次由本机 `update` 记录的会话（同时含二进制暂存路径和配置快照路径）；带 `--to <backup-id>` 时使用指定会话或配置快照 ID。
  - 若指定/最近会话只有配置快照、没有对应二进制暂存记录（例如快照来自手动 `proxyctl backup` 而非 `update`），必须明确报告"仅回滚配置，二进制未变更"，不得假装完成了二进制回滚。
  - 找不到任何可用快照/会话时明确报错，不做静默无操作。
- 下载失败、校验失败必须在替换二进制之前发现；已下载的临时文件校验失败时删除并保留原二进制不变。
- 脚本收到中断信号（如 `SIGINT`/`SIGTERM`）时，已暂存的旧二进制和会话目录不得被清理逻辑误删，确保中断后仍可手动或下次 `rollback` 恢复。

**不变量：**

- 二进制替换前，原 `proxyctl` 必须仍可用（不得先删除旧二进制再下载新的），且暂存副本必须先于替换动作落盘并可独立校验。
- `update` 自动回滚（二进制 + 配置）只使用本次 update 创建的会话，不得选择任意历史快照。
- 配置回滚路径复用 Task 3 的 `proxyctl restore`，不重新实现文件恢复逻辑；二进制回滚是 `install-proxy.sh` 自身职责（`proxyctl restore` 不覆盖自身可执行文件）。
- 二进制回滚前必须校验暂存文件的 SHA-256 与暂存时记录一致，防止暂存期间被篡改或磁盘错误导致回滚到损坏二进制。
