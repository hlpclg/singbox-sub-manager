# v0.5 远程节点健康检查 — 设计文档

- 日期：2026-08-13
- 版本目标：v0.5.0
- 范围：探测 `nodes.conf` 中外部 Hysteria2 节点是否真实可用 (Remote Health)。

## 背景
在 v0.4 中，我们实现了对订阅中心本机的健康检查（Caddy, sing-box, 配置, 端口等）。根据设计，针对远程 Hysteria2 节点的探测（Remote Health）被推迟至 v0.5。
简单的 Ping 或 UDP 端口探测（v0.5-a）不足以验证 Hysteria2 节点的可用性（密码错误或协议被阻断都会导致不可用）。因此，必须实现完整的 Hysteria2 认证握手与实际代理请求（v0.5-b）。

## 核心设计：动态 sing-box 子进程探测
为了避免在 Go 代码中维护复杂的 Hysteria2 协议栈，我们复用系统中已有的 `sing-box` 二进制文件。

**探测流程**：
1. **配置生成**：为待测节点生成一个临时的 `sing-box` JSON 配置，配置一个本地 `mixed` (SOCKS5/HTTP) inbound（分配随机可用端口），以及对应的 `hysteria2` outbound。
2. **启动进程**：使用 `exec.CommandContext` 启动 `sing-box run -c <temp.json>`。
3. **可用性等待**：循环检查或等待该本地端口开启监听。
4. **代理请求**：使用 HTTP 客户端通过该本地代理发起 GET 请求至可靠端点（如 `http://cp.cloudflare.com/generate_204`）。
5. **清理资源**：无论成功失败，关闭子进程并删除临时配置。
6. **判定**：若能在超时时间（如 10 秒）内获得预期的 HTTP 204 响应，则视为 `PASS`，否则为 `FAIL`。

## CLI 接口

1. **单节点测试**：
   `proxyctl node test <name>`
   测试指定节点，输出详细的延迟或错误原因。

2. **全局远程测试**：
   `proxyctl health --remote`
   在现有的本机健康检查基础上，附加对 `nodes.conf` 中所有 `ENABLED=true` 的节点进行远程健康检查。

## 并发控制
如果节点较多，串行探测会非常耗时。
- 在 `health --remote` 中，引入一个并发度为 4 的 Worker Pool。
- 每个节点探测有独立的 `context.WithTimeout`（如 10 秒）。
- 全局命令有一个总超时兜底（如 60 秒）。

## 错误处理与安全
- **资源泄漏**：确保在任何情况下（崩溃、超时）`sing-box` 子进程都能被正确 `Kill`，避免僵尸进程和端口占用。
- **敏感信息**：日志和输出中不得打印节点密码和 OBFS 密码。生成的临时配置文件需存放在 `/tmp` 下，并在测试结束后强制删除。

## 后续演进
v0.5 仅实现探测和状态展示。基于这些探测结果的“自动禁用失效节点”（Auto-disable）将作为后续增强。
