# v0.6 健康监控与保守自动恢复 — 设计文档

- 日期：2026-08-13
- 版本目标：v0.6.0
- 状态：设计已批准，待实施
- 范围：周期性执行现有健康检查，在严格阈值和冷却约束下自动重启本机服务。

## 1. 背景与目标

v0.4 已提供订阅中心本机健康检查，v0.5 已提供远程 Hysteria2 节点真实代理探测，但两者均依赖人工调用。v0.6 将这些检测能力接入 systemd 定时调度，并只对明确归属于本机服务的持续故障执行有限恢复。

目标：

- 无人值守地发现本机及远程节点故障。
- 过滤瞬时失败，避免因单次探测抖动重启服务。
- 自动恢复仅限本机 `sing-box` 和 `caddy`。
- 所有决策可追溯、可测试，进程重启后不丢失阈值及冷却状态。

## 2. 非目标

v0.6 不包含：

- 修改或修复 sing-box、Caddy、订阅及节点配置。
- SSH、API 或其他形式的远程恢复操作。
- 邮件、Webhook、短信或第三方告警渠道。
- VLESS Reality、TUIC 等新协议。
- Rocky Linux、AlmaLinux、Amazon Linux 等 RPM 系适配。
- 通用升级、备份、回滚或卸载能力。
- 常驻 daemon；调度和日志分别由 systemd timer 与 journald 提供。

## 3. CLI 契约

新增单次执行命令：

```text
proxyctl monitor
```

该命令负责读取状态、执行当轮检查、计算恢复动作、按需重启及复检、原子写回状态，然后退出。命令自身不循环、不创建 goroutine 型后台任务。

命令须支持安装生成的固定配置，使 systemd unit 无需拼装复杂参数。面向人工诊断的 `proxyctl health` 和 `proxyctl health --remote` 行为及既有输出 schema 保持兼容。

退出码：

- `0`：当轮最终健康，或发现故障但尚未达到恢复阈值。
- `1`：达到阈值后的恢复失败，或恢复后复检仍失败。
- `2`：当轮存在仅记录的降级或远程节点故障。
- `3`：参数、状态文件、配置或内部执行错误，无法可靠完成决策。

`monitor` 输出一条机器可读的 JSON 结果到标准输出，至少包含执行时间、检查摘要、服务决策、执行动作、复检结果和远程检查摘要。不得输出密码、token、完整节点 URI 或临时 sing-box 配置。

## 4. 调度契约

安装器新增并启用：

- `proxyctl-monitor.service`：`Type=oneshot`，执行一次 `proxyctl monitor`。
- `proxyctl-monitor.timer`：本机检查周期为 5 分钟，并设置持久化调度，使主机短暂停机后能够补跑。

远程节点检查不另建 timer。`monitor` 根据持久化的最近远程检查时间决定是否附加远程检查，默认间隔 30 分钟。首次运行应执行远程检查；尚未到间隔时只执行本机检查。

同一时刻最多存在一个 monitor 实例。并发启动必须通过进程级锁确定性拒绝或串行化，不得并发读写状态或重复重启服务。单次运行须有总超时；取消和超时必须传播到健康检查、服务控制及复检路径，并仍安全释放锁和临时资源。

## 5. 状态模型与持久化

状态文件固定为：

```text
/var/lib/singbox-sub-manager/monitor-state.json
```

状态按服务分别保存，至少包含：

- 连续失败次数。
- 最近一次检查时间及结果。
- 最近一次恢复尝试时间及结果。
- 冷却截止时间。
- 最近一次远程检查时间。
- schema 版本。

写入必须采用“同目录临时文件 + `fsync` + 原子 rename”，文件权限为 `0600`。写入失败时不得破坏上一个有效状态。

状态文件不存在视为首次运行。状态损坏、schema 不支持或权限错误属于内部错误：当轮可以执行只读检查并报告结果，但不得自动重启任何服务，也不得覆盖损坏状态。时间判断使用 UTC；若检测到系统时间倒退，冷却期采取保守解释，不得因此提前重启。

## 6. 故障归属与阈值

恢复判断只使用稳定 check ID，不使用整体 `unhealthy` 结论或错误文本匹配。

`sing-box` 触发集合：

- `service.singbox`
- `port.udp443`

`caddy` 触发集合：

- `service.caddy`
- `port.tcp443`
- `port.tcp80`

同一服务的触发集合中任一检查为 `fail`，该服务当轮记为一次失败；全部通过则清零连续失败次数。`warn` 不增加失败次数，也不触发恢复。

连续失败达到 3 次才具备恢复资格。前三轮含义为：第 1、2 次只记录；第 3 次若不在冷却期则尝试恢复。进程重启不得重置计数。

其他检查（配置、订阅文件、HTTPS、TLS、DNS、磁盘及远程节点）只影响报告，不触发服务重启，避免用重启掩盖配置、证书、存储或网络问题。

## 7. 恢复动作与冷却

恢复命令仅为：

```text
systemctl restart sing-box
systemctl restart caddy
```

约束：

- 每轮每个服务最多执行一次 restart。
- 两个服务同时达到阈值时分别决策和执行，一个失败不跳过另一个。
- 每次 restart 都必须有独立超时并响应上层取消。
- restart 成功后立即只复检该服务的触发集合。
- restart 命令失败或复检失败均记为恢复失败。
- 恢复尝试后立即进入 30 分钟冷却，无论恢复成功或失败，冷却期内不得再次重启。
- 恢复后复检全部通过则清零该服务连续失败次数；否则保留至少阈值值，使冷却结束后仍需先经过新一轮检查才能再次决策。
- 不调用 `enable`、`daemon-reload`、配置生成或包管理命令。

## 8. 远程节点策略

达到 30 分钟间隔时，复用 v0.5 的远程节点检查能力，对所有 `ENABLED=true` 节点执行有界并发探测。远程结果仅写入本轮输出和 journald，并更新最近远程检查时间。

远程检查失败不得：

- 增加本机服务的连续失败次数。
- 重启本机服务。
- 修改节点状态或配置。
- 连接远程管理端口或执行远程命令。

远程总超时沿用 v0.5 的全局上限。即使远程检查超时，本机状态更新及已经完成的本机恢复结果仍须安全落盘。

## 9. 组件边界

实现应分为可独立测试的职责：

- monitor 编排器：控制单轮数据流、取消、超时和退出结果。
- 策略决策器：纯逻辑，根据检查结果、旧状态和当前时间生成新状态及动作计划。
- 状态仓库：加载、校验及原子持久化 JSON。
- 服务控制器：封装有界的 `systemctl restart`。
- 调度安装：由安装器写入固定 systemd service/timer 并启用。

策略决策器不得直接执行 I/O；服务控制器不得自行决定阈值；状态仓库不得隐式修复损坏状态。

## 10. 失败处理与安全性

- 无 root 权限或无法控制 systemd 时，报告明确错误，不尝试权限提升。
- 状态在读取后、落盘前若进程取消，不执行新的恢复动作；已完成的动作必须尽最大努力记录，记录失败则以内部错误退出并写 journald。
- 日志仅包含 check ID、服务名、计数、阈值、冷却截止时间和脱敏错误类别。
- 安装或升级 systemd unit 时使用临时文件和原子替换；写入成功后才执行 `daemon-reload` 和启用 timer。
- 安装失败不得破坏原有 `proxyctl`、健康检查或服务运行状态。

## 11. 测试与验收

确定性单元测试必须覆盖：

- 第 1、2 次失败不恢复，第 3 次失败恢复。
- 任一归属检查失败只影响对应服务。
- 成功轮清零连续失败次数，`warn` 不增加计数。
- 两个服务同时失败时独立决策，每轮各最多重启一次。
- 冷却期阻止恢复，冷却结束后允许在新检查轮重新决策。
- 重启成功后的复检成功与失败。
- restart 命令失败、超时和取消。
- 状态首次创建、跨进程恢复、权限、损坏 schema、原子写失败及时间倒退。
- 远程检查的首次执行、30 分钟节流、失败隔离、取消及全局超时。
- 锁竞争不会重复检查、写状态或重启。

Shell 测试必须覆盖 systemd unit/timer 内容、权限、幂等安装和失败不破坏旧文件。Shell 文件变化后执行对应 `shellcheck`。

实施完成前按仓库全局门禁在 Go 1.22 容器中执行：

```text
go test -race -count=1 ./...
go vet ./...
gofmt -l .
git diff --check
```

其中 `gofmt -l .` 必须无输出；并发上限、取消传播、资源释放和状态逻辑必须由确定性测试证明，race 检测仅作补充。
