# v0.6 健康监控与保守自动恢复 — 设计文档

- 日期：2026-08-13
- 版本目标：v0.6.0
- 状态：已实施并合并（`b167df1`，发布标签 `v0.6.0`）
- 范围：周期性执行现有健康检查，在严格阈值和冷却约束下自动重启本机服务。

## 1. 背景与目标

v0.4 已提供订阅中心本机健康检查，v0.5 已提供远程 Hysteria2 节点真实代理探测，但两者均依赖人工调用。v0.6 将这些检测能力接入 systemd 定时调度，并只对明确归属于本机服务的持续故障执行有限恢复。

目标：

- 无人值守地发现本机及远程节点故障。
- 过滤瞬时失败，避免因单次探测抖动重启服务。
- 自动恢复仅限本机 `sing-box` 和 `caddy`。
- 所有决策可追溯、可测试，进程重启后不丢失阈值及冷却状态。

## 2. 非目标

v0.6 不包含：

- 修改或修复 sing-box、Caddy、订阅及节点配置。
- SSH、API 或其他形式的远程恢复操作。
- 邮件、Webhook、短信或第三方告警渠道。
- VLESS Reality、TUIC 等新协议。
- Rocky Linux、AlmaLinux、Amazon Linux 等 RPM 系适配。
- 通用升级、备份、回滚或卸载能力。
- 常驻 daemon；调度和日志分别由 systemd timer 与 journald 提供。

## 3. CLI 契约

新增单次执行命令：

```text
proxyctl monitor
```

该命令负责读取状态、执行当轮检查、计算恢复动作、按需重启及复检、原子写回状态，然后退出。命令自身不循环、不创建 goroutine 型后台任务。

命令须支持安装生成的固定配置，使 systemd unit 无需拼装复杂参数。面向人工诊断的 `proxyctl health` 和 `proxyctl health --remote` 行为及既有输出 schema 保持兼容。

退出码：

- `0`：当轮最终全部健康。
- `1`：已执行恢复，但 restart 失败或恢复后复检仍失败。
- `2`：存在故障或降级，但未发生失败的恢复；包括尚未达到阈值、正在冷却、远程节点失败、暂停状态下发现故障、恢复资格预检否决，以及恢复成功后仍有其他仅记录的故障。
- `3`：参数、状态文件、配置或内部执行错误导致无法可靠决策。

`monitor` 输出一条机器可读的 JSON 结果到标准输出，至少包含执行时间、检查摘要、服务决策、执行动作、复检结果和远程检查摘要。不得输出密码、token、完整节点 URI 或临时 sing-box 配置。

## 4. 调度契约

安装器新增并启用：

- `proxyctl-monitor.service`：`Type=oneshot`，执行一次 `proxyctl monitor`；设置 `SuccessExitStatus=2`，使“已检查但无需恢复的降级”不把 unit 标记为失败。
- `proxyctl-monitor.timer`：使用 `OnCalendar=*:0/5`、`Persistent=true`、`AccuracySec=15s` 和 `RandomizedDelaySec=15s`。`Persistent=true` 仅保证开机后补触发一次错过的 calendar 调度，不补齐停机期间每个五分钟周期。

远程节点检查不另建 timer。`monitor` 根据持久化的最近远程检查时间决定是否附加远程检查，默认间隔 30 分钟。首次运行应执行远程检查；尚未到间隔时只执行本机检查。

同一时刻最多存在一个 monitor 实例。并发启动必须通过进程级锁确定性拒绝或串行化，不得并发读写状态或重复重启服务。单次运行须有总超时；取消和超时必须传播到健康检查、服务控制及复检路径，并仍安全释放锁和临时资源。

## 5. 状态模型与持久化

状态文件固定为：

```text
/var/lib/singbox-sub-manager/monitor-state.json
```

暂停标记独立于状态 JSON：

```text
/var/lib/singbox-sub-manager/monitor-paused
```

状态顶层至少包含 schema 版本、按服务划分的状态和全局远程检查状态：

```json
{
  "schema_version": 1,
  "services": {
    "sing-box": {},
    "caddy": {}
  },
  "remote": {
    "last_check_at": "2026-08-13T00:00:00Z"
  }
}
```

每个服务状态至少包含：

- 连续失败次数。
- 最近一次检查时间及结果。
- 最近一次恢复尝试时间及结果。
- 冷却截止时间。
- 是否存在尚未完成最终记账的恢复尝试。

写入必须采用“同目录临时文件 + 文件 `fsync` + 原子 rename + 父目录 `fsync`”，文件权限为 `0600`。写入失败时不得破坏上一个有效状态。

状态文件不存在视为首次运行。状态损坏、schema 不支持或权限错误属于内部错误：当轮可以执行只读检查并报告结果，但不得自动重启任何服务，也不得覆盖损坏状态。时间判断使用 UTC；若检测到系统时间倒退，冷却期采取保守解释，不得因此提前重启。

## 6. 故障归属与阈值

恢复判断只使用稳定 check ID，不使用整体 `unhealthy` 结论或错误文本匹配。

`sing-box` 触发集合：

- `service.singbox`
- `port.udp443`

`caddy` 触发集合：

- `service.caddy`
- `port.tcp443`
- `port.tcp80`

同一服务的触发集合中任一检查为 `fail`，该服务当轮记为一次失败；全部通过则清零连续失败次数。`warn` 不增加失败次数，也不触发恢复。

连续失败计数为饱和计数：`failure_count = min(failure_count + 1, 3)`。第 1、2 次失败只记录；第 3 次进入恢复资格预检。进程重启不得重置计数。

冷却期内的新一轮 `fail` 保持计数为 3，`pass` 清零。冷却结束后的第一轮新 `fail` 才允许重新进入恢复资格预检；不得仅因 timer 唤醒或旧状态已达阈值而恢复。

其他检查（配置、订阅文件、HTTPS、TLS、DNS、磁盘及远程节点）只影响报告，不触发服务重启，避免用重启掩盖配置、证书、存储或网络问题。

## 7. 暂停与恢复资格预检

管理员控制接口固定为：

```text
proxyctl monitor pause
proxyctl monitor resume
proxyctl monitor status
```

`pause` 原子创建独立暂停标记并同步父目录。暂停期间本机检查继续、远程检查仍按 30 分钟节流执行、结果继续输出并进入 journald，但不增加任何服务的失败计数，也不执行 restart。即使状态 JSON 损坏，`pause` 仍必须可用。

`resume` 先加载有效状态并原子持久化两个服务归零后的失败计数，再删除暂停标记并同步父目录；既有冷却截止时间不清除，下一轮从零重新累计。状态损坏或任一步持久化失败时返回退出码 3 并保留暂停标记。`status` 只读取暂停标记和可用状态，不执行检查、状态迁移或恢复动作。

`pause`、`resume` 和定时监控轮次共用同一进程锁，避免与恢复预提交或状态更新竞态。`pause` 成功返回只保证其后的轮次不再恢复；调用前已经执行的 restart 不可撤销。`status` 可无锁读取暂停标记，但读取状态 JSON 时必须容忍恰好发生的原子替换。

服务达到阈值后必须经过恢复资格预检。以下任一条件否决恢复：

- monitor 已暂停。
- 状态无效或无法可靠持久化。
- 目标服务所需端口被其他进程或 systemd unit 占用。
- 端口归属无法可靠判定。
- 对应服务配置检查失败：`config.singbox` 否决 sing-box，`config.caddy` 否决 Caddy。

端口归属属于 monitor 的恢复资格事实，不改变 v0.4/v0.5 的稳定 health check ID 或输出 schema。目标端口无人占用或能可靠归属于目标服务时，端口归属预检通过；检测必须有界、可取消且可注入测试。普通预检否决只报告降级并返回退出码 2，不执行 restart；状态无效或无法持久化属于无法可靠决策，禁止恢复并返回退出码 3。

## 8. 恢复动作与冷却

恢复命令仅为：

```text
systemctl restart sing-box
systemctl restart caddy
```

约束：

- 每轮每个服务最多执行一次 restart。
- 两个服务同时达到阈值时分别决策和执行，一个失败不跳过另一个。
- 每次 restart 都必须有独立超时并响应上层取消。
- restart 成功后立即只复检该服务的触发集合。
- restart 命令失败或复检失败均记为恢复失败。
- 预检通过后必须先原子持久化 `recovery_in_progress=true`、恢复尝试时间及 30 分钟冷却截止时间，再执行 restart。预提交失败时禁止执行 restart。
- restart 和复检结束后再次原子写入最终结果并清除 `recovery_in_progress`。进程在预提交后崩溃时，下一轮保持冷却并报告未完成的恢复尝试，不得立即重复 restart。
- 恢复尝试无论成功或失败都进入 30 分钟冷却；冷却期内不得再次重启。
- 恢复后复检全部通过则清零该服务连续失败次数；否则计数固定为 3。冷却结束后仍须先观察一轮新的 `fail`，再进入恢复资格预检。
- 不调用 `enable`、`daemon-reload`、配置生成或包管理命令。

## 9. 远程节点策略

达到 30 分钟间隔时，复用 v0.5 的远程节点检查能力，对所有 `ENABLED=true` 节点执行有界并发探测。远程结果仅写入本轮输出和 journald，并更新最近远程检查时间。

远程检查失败不得：

- 增加本机服务的连续失败次数。
- 重启本机服务。
- 修改节点状态或配置。
- 连接远程管理端口或执行远程命令。

远程总超时沿用 v0.5 的全局上限。即使远程检查超时，本机状态更新及已经完成的本机恢复结果仍须安全落盘。

## 10. 组件边界

实现应分为可独立测试的职责：

- monitor 编排器：控制单轮数据流、取消、超时和退出结果。
- 策略决策器：纯逻辑，根据检查结果、旧状态和当前时间生成新状态及动作计划。
- 状态仓库：加载、校验及原子持久化 JSON。
- 恢复资格检查器：读取暂停、配置和端口归属事实，只回答是否允许恢复及稳定否决原因。
- 服务控制器：封装有界的 `systemctl restart`。
- 调度安装：由安装器写入固定 systemd service/timer 并启用。

策略决策器不得直接执行 I/O；服务控制器不得自行决定阈值；状态仓库不得隐式修复损坏状态。

## 11. 失败处理与安全性

- 无 root 权限或无法控制 systemd 时，报告明确错误，不尝试权限提升。
- 状态在读取后、落盘前若进程取消，不执行新的恢复动作；已完成的动作必须尽最大努力记录，记录失败则以内部错误退出并写 journald。
- 日志仅包含 check ID、服务名、计数、阈值、冷却截止时间和脱敏错误类别。
- 安装或升级 systemd unit 时使用临时文件和原子替换；写入成功后才执行 `daemon-reload` 和启用 timer。
- 安装失败不得破坏原有 `proxyctl`、健康检查或服务运行状态。

## 12. 测试与验收

确定性单元测试必须覆盖：

- 第 1、2 次失败不恢复，第 3 次失败恢复。
- 任一归属检查失败只影响对应服务。
- 成功轮清零连续失败次数，`warn` 不增加计数。
- 失败计数饱和于 3，不出现无界增长。
- 两个服务同时失败时独立决策，每轮各最多重启一次。
- 冷却期阻止恢复，冷却结束后允许在新检查轮重新决策。
- pause 期间继续检查但不累计、不恢复；resume 清零计数但保留冷却；状态损坏时仍可 pause 且不得 resume。
- pause/resume 与监控轮次的锁竞争不会造成预提交、状态写入或 restart 竞态。
- 外部端口占用、归属未知和对应配置失败分别否决恢复，且不改变既有 health check ID。
- 恢复前预提交失败时不执行 restart；预提交后崩溃的下一轮不重复 restart。
- 重启成功后的复检成功与失败。
- restart 命令失败、超时和取消。
- 状态首次创建、跨进程恢复、权限、损坏 schema、文件及父目录同步失败、原子写失败及时间倒退。
- 远程检查的首次执行、30 分钟节流、失败隔离、取消及全局超时。
- 锁竞争不会重复检查、写状态或重启。
- timer 使用 `OnCalendar` 持久化调度，service 将退出码 2 视为成功。

Shell 测试必须覆盖 systemd unit/timer 内容、权限、幂等安装和失败不破坏旧文件。Shell 文件变化后执行对应 `shellcheck`。

实施完成前按仓库全局门禁在 Go 1.22 容器中执行：

```text
go test -race -count=1 ./...
go vet ./...
gofmt -l .
git diff --check
```

其中 `gofmt -l .` 必须无输出；并发上限、取消传播、资源释放和状态逻辑必须由确定性测试证明，race 检测仅作补充。
