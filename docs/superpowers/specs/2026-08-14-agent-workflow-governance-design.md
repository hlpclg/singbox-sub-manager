# Agent 开发工作流治理设计

- 日期：2026-08-14
- 状态：待用户书面审阅
- 目标：把 v0.6 实施复盘沉淀为项目可共享、全局可复用的强制工作流。

## 1. 背景

v0.6 的设计边界总体完整，但实施和审查经历了多轮返工。主要原因不是功能规格缺失，而是 Task 一次性批量交付、审查问题缺少回归测试闭环、聚焦验证被误述为完整门禁、CI 工具版本不一致，以及修复只覆盖反馈字面而未检查相邻边界。

工作流必须同时解决两个问题：进入本项目的不同 Agent 应得到一致规则；跨项目的通用经验不应在每个仓库重复维护。

## 2. 两层规则结构

### 2.1 本机全局层

在本机 `~/.codex/AGENTS.md` 中维护少量跨项目强制原则：

- 单 Task 闭环后才能进入下一 Task。
- 计划必须把关键不变量映射到确定性验收测试。
- 审查修复必须建立“复现、失败证据、最小修复、通过证据、相邻边界检查”的闭环。
- 聚焦测试、专项门禁和完整门禁必须明确区分。
- 声称完成前必须使用新鲜命令和 Git 差异证明。
- 验证工具必须与 CI 使用的版本或安装来源一致。

全局层不记录项目命令、版本号、文件路径或发布平台。它只提供默认治理规则。

### 2.2 项目层

项目根 `AGENTS.md` 保留项目强制入口和优先级；详细工作流提交到：

```text
docs/agent-workflows/
├── README.md
├── task-lifecycle.md
├── review-closure.md
├── verification-gates.md
└── templates/
    ├── acceptance-matrix.md
    └── handoff.md
```

项目层定义本仓库的 Go 1.22 容器要求、ShellCheck/CI 对齐、Task 提交规则、Git 门禁和交接模板。所有进入仓库的 Agent 都能通过根 `AGENTS.md` 发现这些规则。

## 3. 优先级与冲突处理

规则优先级从高到低为：

1. 用户在当前任务中的明确指令。
2. 已批准的项目设计规范和实施计划中的全局约束。
3. 项目根 `AGENTS.md` 及其引用的 `docs/agent-workflows/`。
4. 本机全局 `~/.codex/AGENTS.md`。
5. Agent 的默认执行习惯。

同级规则冲突，或低层规则无法同时满足高层规则时，Agent 必须停止并报告具体冲突，不得自行选择一种解释继续。

## 4. Task 生命周期

每个 Task 必须依次通过：

```text
契约确认
→ 验收矩阵
→ 最小实施
→ 聚焦测试
→ 规格符合性审查
→ 代码质量审查
→ Task 专项门禁
→ 独立提交
→ 下一 Task
```

不得先完成全部 Task 再统一审查。当前 Task 有未解决的规格或质量问题时，不得开始下一 Task。

验收矩阵至少记录：需求或不变量、主要风险、成功路径、失败路径、取消或超时、确定性测试、验证命令和预期证据。不适用项必须写明原因。

## 5. 审查闭环

每条有效审查发现必须记录：

1. 可复现条件和实际错误行为。
2. 修复前能够失败的测试或最小复现命令。
3. 只针对根因的最小修复。
4. 修复后同一测试通过的证据。
5. 相邻边界检查，包括成功、失败、取消、超时、持久化和清理路径中适用的部分。

不得仅根据审查文字修改条件分支后宣布完成。若修复引入新资源、trap、context、锁、状态字段或 CI 门禁，必须检查它替换或覆盖的既有生命周期。

审查报告应区分：原规格未实现、原规格歧义、修复引入回归、测试缺口、文档不一致。不能把新发现全部归为原计划问题。

## 6. 验证与证据

验证分三级：

- 聚焦测试：开发循环中验证当前最小变更。
- Task 专项门禁：Task 交接前最多运行一次，覆盖该 Task 的完整影响范围。
- 完整门禁：正式交付或合并前运行一次，覆盖仓库规定的全部测试与静态检查。

报告必须准确使用上述名称。聚焦测试通过不得表述为“全部门禁通过”。复用旧证据时必须说明基线、证据时间、未受影响的理由和省略的命令。

CI 使用的工具必须固定版本、固定容器标签或固定安装来源。若 CI 采用系统包，最终验证必须使用相同系统版本和包来源；不得仅以另一版本工具通过作为等价证据。

完成证据至少包括：比较基线、变更文件、验证命令、退出码、首个失败根因或成功结论、暂存文件清单、提交 SHA、提交后工作区状态。

## 7. 会话与交接

设计、计划、实施和下一 Task 原则上使用独立会话。长会话发生上下文压缩后，不在同一会话开启新的实施阶段。

交接必须使用模板，至少包含：目标、批准规范、比较基线、已完成 Task、未解决风险、当前工作区状态、可复用验证证据、下一步聚焦命令。接手 Agent 不得为了保险重复全仓扫描或重跑仍有效的完整门禁。

## 8. 变更范围

本次后续实施只包含：

- 新建 `docs/agent-workflows/` 及六个工作流文件。
- 更新项目根 `AGENTS.md`，加入读取入口、适用时机和优先级。
- 更新本机 `~/.codex/AGENTS.md`，加入跨项目通用规则及项目规则优先说明。

不修改生产代码、CI、项目功能规格或现有历史计划。不把本机全局文件复制进仓库。

## 9. 验收标准

- 从项目根 `AGENTS.md` 能明确找到所有项目工作流文档。
- 项目文档之间没有重复定义或互相冲突的全局约束。
- 验收矩阵和交接模板可以直接复制使用，不依赖本次 v0.6 的上下文。
- 本机全局规则不含本项目专有命令或版本。
- 项目层与全局层明确优先级和冲突停止条件。
- 仓库文档通过 `git diff --check`，且以独立文档提交交付。
- 本机全局文件修改后保留备份或可审阅差异，但不进入任何仓库提交。

## 10. 非目标

- 不创建新的 Agent Skill 或插件。
- 不通过 CI 强制解析 Markdown 工作流。
- 不为每种语言或框架建立独立工作流。
- 不把一次复盘写成事件时间线或责任追踪文档。
