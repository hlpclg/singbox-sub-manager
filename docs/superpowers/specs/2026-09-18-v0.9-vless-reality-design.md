## 1. 背景与目标

`nodes.Node`、`render.Clash`/`render.Shadowrocket`、`health/remote.GenerateConfig` 目前都是 Hysteria2 专用字段和硬编码协议字符串，工具事实上是"Hysteria2 专用工具"。本版本让节点 schema 支持第二种协议，把工具往`plan.md`「第四阶段」目标的"多协议管理工具"方向推进一步，但只落地 VLESS Reality 一种协议，范围收紧到 nodes/render/health 三个包和 CLI 的对应命令。

## 2. 非目标

- **TUIC、Trojan TLS、ShadowTLS、WireGuard、SOCKS5 出站**：留在 `plan.md` 需求池，不在本版本。
- **本机安装 VLESS Reality 服务端**：`install-proxy.sh` 不新增安装/配置 VLESS Reality 服务端（sing-box 或 Xray inbound）的能力；VLESS Reality 节点均为用户在其他机器上自行搭建后录入。
- **installer 首次写入格式不变**：`install-proxy.sh` 全新安装时仍写 legacy pipe 格式（不改成默认写 sectioned）；用户要在同一台机器上首次添加 VLESS Reality 节点，必须先手动执行一次 `proxyctl node migrate`。
- **协议迁移**：`node edit` 不支持把已存在节点的 `Type` 从一种协议改成另一种；改协议＝删除后用新协议重新 `add`。
- **Reality 传输变体**：只支持裸 TCP 传输（Mihomo 侧写 `network: tcp`；sing-box 侧不写 `transport` 字段，两种表达方式见 §7 的说明，字面量不对称，不要混用），不做 gRPC/WebSocket 等传输层组合。
- **`flow`/`fingerprint`/`spiderX` 可配置化**：三者固定为设计中给出的默认值，不开放为节点字段或 CLI flag。
- **legacy pipe 格式扩展**：legacy 6 字段格式继续只服务 Hysteria2；VLESS Reality 节点只能写在 sectioned 格式里。
- **Shell 兜底渲染器同步新协议**：`write_subscriptions_with_shell` 不学习渲染 VLESS Reality，保持单一职责只渲染 legacy 格式，不生成 vless 代理项；遇到 sectioned 格式的拒绝逻辑不在这个函数内部，由调用它的策略层完成（见 §9.3）。

## 3. 节点类型与集中默认值（`internal/nodes`）

```go
type NodeType string

const (
    TypeHysteria2    NodeType = "hysteria2"
    TypeVlessReality NodeType = "vless-reality"
)

const (
    RealityFlow        = "xtls-rprx-vision"
    RealityFingerprint = "chrome"
    RealitySpiderX     = "/"
    RealityNetwork     = "tcp"
)
```

### 3.1 `effectiveType`：唯一的空值归一化点

```go
func effectiveType(t NodeType) NodeType {
    if t == "" {
        return TypeHysteria2
    }
    return t
}
```

- `nodes.Validate`（见 3.3）接受 `Type == ""` 并按 `TypeHysteria2` 规则校验，用于兼容外部直接构造 `Node{}`（包括现有测试）的旧调用方式。
- `Serialize`、`render.Clash`、`render.Shadowrocket`、`health/remote.GenerateConfig` 内部**一律先调用 `effectiveType(n.Type)`** 再做类型分支/输出，不直接比较 `n.Type`。这保证：
  - 磁盘上永远不会出现空 `TYPE=`（`Serialize` 用 `effectiveType` 算出的值写 `TYPE=hysteria2`，不是把原始空字符串写出去）。
  - `Node{Type: ""}` 在两个 renderer 里都被当作 Hysteria2 渲染，不会走进 vless 分支或报"未知类型"。
- 解析路径（`parseLegacy`、`parseSectioned` 的隐式 hysteria2 分支）在返回前**显式赋值** `Type = TypeHysteria2`，不依赖 `effectiveType` 兜底——内存中的 `Node`（除测试直接构造的以外）永远有具体类型，`effectiveType` 只是防御性归一化，不是常规路径依赖的机制。

### 3.2 结构体

```go
type Node struct {
    Name    string
    Type    NodeType
    Server  string
    Port    int
    SNI     string
    Enabled bool

    Password     string // hysteria2-only
    ObfsPassword string // hysteria2-only

    UUID      string // vless-reality-only
    PublicKey string // vless-reality-only，Reality 公钥
    ShortID   string // vless-reality-only，可为空
}
```

字段本身不互斥（Go 没有真正的联合类型），互斥关系由 3.3 的 `Validate` 与第 4 节的解析期字段集校验共同强制。

### 3.3 `nodes.Validate`（导出，唯一规则实现）

```go
func Validate(n Node) error
```

- 内部即当前 `validateFields` 逐步演进为公开函数（原 `validateFields` 保留作为内部别名或直接改名导出，二选一在实施时定，不影响契约）。
- 公共字段：`Name`（`ValidateName`）、`Server`、`Port ∈ [1,65535]` 两种类型都必须非空/有效。
- 按 `effectiveType(n.Type)` 分支：
  - `TypeHysteria2`：`Password`/`ObfsPassword`/`SNI` 必须非空；`UUID`/`PublicKey`/`ShortID` 必须为空，否则报错 `node %q: vless-reality fields not allowed on hysteria2 node`。
  - `TypeVlessReality`：
    - `SNI` 非空。
    - `UUID` 非空，且匹配 `^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$`（比 Xray 的任意字符串+UUIDv5 映射更严，但与 sing-box 一致，健康探测跑的正是 sing-box，故按 sing-box 的要求收紧）。
    - `PublicKey` 非空，用 `base64.RawURLEncoding.Strict()` 解码成功且长度恰为 32 字节（x25519 公钥长度）。**只接受**不带填充的 URL-safe base64；带 `=` 填充或标准字母表（`+`/`/`）的输入直接报错，错误信息写明期望格式（"expected unpadded base64url, e.g. output of `sing-box generate reality-keypair`"），不做归一化重编码——校验函数只拒绝或接受，不改写字段。
    - `ShortID` 允许为空；非空时必须是偶数长度、≤16 个十六进制字符（`^([0-9a-fA-F]{2}){1,8}$`）。
    - `Password`/`ObfsPassword` 必须为空，否则报错 `node %q: hysteria2 fields not allowed on vless-reality node`。
  - 未知的非空 `Type`（不等于两个常量之一）：报错 `node %q: unknown type %q`。
- **完整校验顺序**（显式定死，不止"CHANGE_ME 在格式校验之前"一句）：
  1. `ValidateName(n.Name)`。
  2. 公共必填字段非空/有效：`Server`、`Port ∈ [1,65535]`、`SNI`（现状已有，沿用）。
  3. `CHANGE_ME` 占位符子串匹配：覆盖 `Name/Server/SNI` 以及该类型的凭据字段（Hysteria2 的 `Password/ObfsPassword`；VlessReality 的 `UUID/PublicKey/ShortID`），命中就直接返回"replace placeholder secret in field %s (CHANGE_ME)"。
  4. 跨类型字段拒绝：命中即返回"vless-reality/hysteria2 fields not allowed on ... node"（3.3 前文已定义）。
  5. 该类型专属字段的格式校验（UUID 正则 / base64 解码 / short_id 正则）。
  这个顺序保证 CHANGE_ME 占位符（步骤 3）永远先于格式校验（步骤 5）被识别，不会先报出"invalid uuid format"这类不知所云的错误；这与现状对 Hysteria2 的行为一致，只是把完整顺序显式写下来，避免未来重排代码时不小心让某一步抢跑。

### 3.4 校验调用点（不是"唯一入口"而是"唯一实现，多处调用"）

`nodes.Validate` 被以下路径调用，覆盖所有能把 `Node` 数据落地或对外输出的地方：

| 调用方 | 时机 |
|---|---|
| `parseLegacy` / `parseSectioned` | 每个节点构造完成后（现状已有，沿用） |
| `Add` / `Replace` | 现状已有，沿用 |
| `WriteFile`（新增） | 落盘前对整个 slice 逐个校验，任何一个失败则整体不写 |
| `GenerateConfig`（新增） | 生成 sing-box outbound 前先校验该节点 |
| `render.Write`（新增） | 调用 `Clash`/`Shadowrocket` 前对整个 slice 逐个校验，任一失败则不创建输出目录、不写文件（沿用 v0.8 已有的"冲突时不动已有文件"契约，见 `render.CheckNodeNames` 附近逻辑） |

`render.Clash`/`render.Shadowrocket` 本身**签名不变**（`([]nodes.Node) string`，无 error 返回），文档注释明确写明：调用者必须保证传入数据已通过 `nodes.Validate`；在本仓库中这一契约由 `render.Write` 保证，`cmd/proxyctl/main.go` 的 `cmdValidate` 也直接调用这两个函数（不经过 `render.Write`），因此第 8 节要求 `cmdValidate` 自己先对每个节点跑一遍 `nodes.Validate`；直接调用这两个函数的新代码（如测试）需自行保证输入合法或接受未定义渲染结果。

同理，`health/remote.GenerateConfig` 除了 `node test`（`checker.go` 的 `CheckNode`）以外，还被 `proxyctl health --remote` 和 `proxyctl monitor` 两条路径调用；这两处都经过 `remote.CheckNode` → `GenerateConfig`，前置校验点不变，仅在此注明覆盖范围。

`Serialize` 遇到 `effectiveType` 归一化后仍不是 `TypeHysteria2`/`TypeVlessReality` 的值（即调用方跳过了 `Validate` 直接构造非法 `Node`）时，行为未定义——`Serialize` 本身不做类型校验，只在 `WriteFile` 已经对整个 slice 跑过 `Validate` 的前提下才保证输出合法；直接调用 `Serialize`（如测试）必须自行保证输入已合法。

## 4. sectioned 文本格式

### 4.1 判别字段位置规则

- "第一个 key"指一个 section 内，跳过空行和 `#` 注释后第一条 `KEY=VALUE` 行（复用现有 `isMeaningful`）。
- 若该行的 key 是 `TYPE`：value 必须恰为 `hysteria2` 或 `vless-reality` 之一，否则报错 `line %d: empty TYPE value` （空值）或 `line %d: unknown TYPE %q`（其他非法值）——**不允许** `TYPE=` 通过 `effectiveType` 悄悄归一化成 hysteria2。归一化只发生在"整个 section 没有 `TYPE` key"这一种情况下，不覆盖"写了 `TYPE` 但值非法"这种情况；这是为了不破坏 3.1 定下的"磁盘上永不出现空/非法 `TYPE`"不变量：写入侧靠 `Serialize` 保证，读取侧靠这条规则保证，两边都要卡住才算数。合法值时该 section 进入"显式类型模式"，`cur.Type` 立即赋值，后续 key 只允许该类型的字段集合（见 4.2）。
- 若该行的 key 不是 `TYPE`（包括旧文件没有 `TYPE` 的情况）：该 section 进入"隐式 hysteria2 模式"，`cur.Type = TypeHysteria2`，后续 key 只允许现有 6 个 hysteria2 字段（不含 `TYPE`）——**隐式模式下再出现 `TYPE=` 是错误**（`line %d: TYPE must be the first key in section %q`），不允许"迟到的" TYPE 悄悄切换类型。
- 同一 section 内任何 key（包括 `TYPE`）重复出现是错误（`line %d: duplicate key %q in section %q`），不再是"后值覆盖前值"。
- 上面两条错误规则在具体实现里按检查顺序互斥、不会重叠触发（"隐式模式下迟到的 TYPE"先命中"TYPE must be the first key"就返回，不会继续走到 4.2 的 unknown-key 检查；显式模式下重复的第二个 `TYPE` 先命中"duplicate key"就返回，不会继续走到"只允许出现一次"的表述——4.2 那句是对读者的说明，不是额外一次独立检查）。
- **空 section**（只有 `[NAME]` 头、没有任何 key 就遇到下一个 section 或文件结尾）：报错 `line %d: section %q has no keys`（带行号前缀，与本节其他错误格式一致），不是现状"缺 PORT"这种误导性错误。
- **只写了 `TYPE=vless-reality` 就没有其他 key**：`flush` 阶段的缺字段检查按 `effectiveType` 的完整必填集合判定，检查顺序为"公共字段（`SERVER`/`PORT`/`SNI`）→ 类型专属字段"——这个例子里 `PORT` 确实缺失，报 `missing PORT` 是对的，不是误导；真正要堵的漏洞是"不能报出跨类型的缺字段提示"，即 vless-reality 节点不会被提示缺 `PASSWORD`，hysteria2 节点不会被提示缺 `UUID`。

### 4.2 按类型的允许 key 集合

```
公共：SERVER, PORT, SNI, ENABLED
hysteria2 专属：PASSWORD, OBFS_PASSWORD
vless-reality 专属：UUID, PUBLIC_KEY, SHORT_ID
```

显式模式下 `TYPE` 本身只允许出现一次（即第一行）；出现不属于当前类型允许集合的 key（例如 `vless-reality` 模式下出现 `PASSWORD`）报错 `line %d: unknown key %q for type %q`。

### 4.3 `Serialize` 字段顺序

```
[NAME]
TYPE=hysteria2|vless-reality        # 用 effectiveType(n.Type) 算出，永不为空
SERVER=...
PORT=...
PASSWORD=...          # 仅 hysteria2
OBFS_PASSWORD=...     # 仅 hysteria2
UUID=...              # 仅 vless-reality
PUBLIC_KEY=...        # 仅 vless-reality
SHORT_ID=...          # 仅 vless-reality（可为空字符串）
SNI=...
ENABLED=...
```

每个节点只输出自己类型允许的字段，不写对方协议的空字段。

### 4.4 legacy pipe 格式

不变：6 字段固定顺序，隐式 `Type = TypeHysteria2`，不支持也不校验 `TYPE` 概念。

## 5. CLI（`cmd/proxyctl/node.go`）

- `node add` 新增 flag：`--type`（默认 `"hysteria2"`，保持旧脚本/习惯不变）、`--uuid`、`--public-key`、`--short-id`。
  - 按 `--type` 决定 `resolveField` 询问哪一组必填字段（`hysteria2` 问 password/obfs-password；`vless-reality` 问 uuid/public-key，short-id 不強制询问，允许留空）。
  - 用 `fs.Visit` 记录哪些 flag 被显式传入；若 `--type vless-reality` 但显式传了 `--password` 或 `--obfs-password`（或反过来），直接报错并指出冲突的 flag 名，不静默丢弃。
- `node edit`：不新增 `--type`（协议不可迁移，见第 2 节非目标）。若对目标节点当前类型传入不属于该类型的 flag（同样用 `fs.Visit` 检测），报错拒绝，不依赖 `nodes.Replace`→`Validate` 兜底才发现问题（提前给出更明确的错误）。
- `node list` 表格新增 `TYPE` 列：`NAME  TYPE  SERVER:PORT  SNI  ENABLED`。

## 6. 渲染契约

### 6.1 Mihomo（`render.Clash`）

VLESS Reality 代理项，引号风格与现有 Hysteria2 分支一致（可变字符串值用 `%q`，协议关键字/布尔值不加引号）：

```yaml
  - name: "JP-Reality"
    type: vless
    server: "1.2.3.4"
    port: 443
    uuid: "..."
    network: tcp
    tls: true
    servername: "..."
    flow: xtls-rprx-vision
    client-fingerprint: chrome
    reality-opts:
      public-key: "..."
      short-id: "..."
```

- `network`/`flow`/`client-fingerprint` 来自第 3 节常量；`tls: true`、`servername` 不可省略（Mihomo 要求）。
- **有意不输出** `alpn`/`skip-cert-verify`（Hysteria2 分支里有的两个字段）：`alpn` 不适用于 Vision-over-raw-TCP；Reality 用固定公钥做服务端身份校验，`skip-cert-verify` 没有意义。这是设计选择，不是遗漏，实施与审查按"逐字段对照"验收时不要把这两个字段的缺席当 bug。
- `short-id` 恰为 `n.ShortID`：即使是空字符串也照常输出 `short-id: ""`，不省略这个 key（sing-box/Mihomo 都能接受空 short_id，省略 key 和空字符串在部分版本行为不一致，固定为"总是输出"避免歧义）。
- 策略组、规则集部分不变（v0.8 已确定，与协议无关）。

### 6.2 Shadowrocket（`render.Shadowrocket`）

```
vless://<uuid>@<host>?encryption=none&flow=xtls-rprx-vision&fp=chrome&pbk=<publickey>&security=reality&sid=<shortid>&sni=<sni>&spx=%2F&type=tcp#<name>
```

（参数顺序按 `url.Values.Encode()` 的字母序实际输出写的示例，不是手工排的；`url.Values` 本身不保证顺序稳定性之外的任何顺序契约，第 10 节"逐字段对照"验收时按字母序核对即可，不需要另外约束顺序。）

- 查询参数用 `url.Values` 构造（`Encode()` 输出）。
- `<host>` 用 `net.JoinHostPort(n.Server, strconv.Itoa(n.Port))` 拼接，同时把现有 Hysteria2 分支里的 `fmt.Sprintf("%s:%d", ...)` 一并改成 `net.JoinHostPort`（顺手修掉现有 IPv6 地址拼接的潜在问题，这行代码本次改动必须touch；对 IPv6 server 这会改变现有 Hysteria2 节点 `sr.txt` 的输出字节，见第 10 节回归红线的豁免说明）。
- **不设 URL Path**（现有 Hysteria2 分支设了 `Path: "/"`，`internal/render/render.go:67`；vless 分支不需要，实施时不要照抄这一行）。
- `<name>` 继续放在 URL Fragment（`url.URL.Fragment`），与现有 Hysteria2 行为一致。
- **契约**：每个启用节点在输出里恰好对应一行（顺序与输入的 `ns` 顺序一致），不合并、不跳过——这一点被第 8 节 `cmdValidate` 的行数校验依赖，此处显式写明，不只是隐含在实现里。

## 7. 健康探测（`internal/health/remote/config.go`）

`GenerateConfig` 按 `effectiveType(n.Type)` 分支生成 sing-box outbound；hysteria2 分支不变，新增：

```json
{
  "type": "vless",
  "tag": "proxy",
  "server": "...",
  "server_port": 443,
  "uuid": "...",
  "flow": "xtls-rprx-vision",
  "tls": {
    "enabled": true,
    "server_name": "...",
    "utls": { "enabled": true, "fingerprint": "chrome" },
    "reality": { "enabled": true, "public_key": "...", "short_id": "..." }
  }
}
```

- **不写 `network` 字段。** sing-box outbound 的 `network` 是"启用哪些底层网络"的开关（`tcp`/`udp`，省略即默认两者都启用），语义与 §6.1 Mihomo `network: tcp`（选择传输层为裸 TCP）**不是同一个概念**——两处字面量相同但含义不同，容易被当成对称字段抄错。裸 TCP 传输在 sing-box 里的表达方式是**不写 `transport` 字段**（省略即默认裸 TCP），本设计不需要 `transport`，所以两个字段都不出现在这份 JSON 里。如果误写 `"network": "tcp"`，效果是关闭该 outbound 的 UDP，对当前用途（`checker.go` 只发一次 HTTP GET 测试连通性）没有影响，但一旦这份 `GenerateConfig` 被复用去生成本机 sing-box 客户端配置，会造成 VLESS 节点 UDP 静默失效。
- `short_id` 恰为 `n.ShortID`：即使是空字符串也照常输出 `"short_id": ""`，不省略这个 key（与 §6.1 的"总是输出"决定保持三处一致：Mihomo YAML、Shadowrocket URI 的 `sid=`、这里）。

`CheckNode`/`checker.go` 协议无关，不改动——它只是跑本机 sing-box 加载生成的配置再测代理，两种协议共用同一条探测路径。

## 8. `cmdValidate`（`cmd/proxyctl/main.go`）修复

- 删除硬编码的 hysteria2 专属字段校验（现有 `main.go:112-121`），改为对每个节点调用 `nodes.Validate(n)`。
- Shadowrocket URI 校验（现有 `main.go:139-151`）：
  - 先处理空输出边界：`sr := render.Shadowrocket(ns)`，若 `strings.TrimSpace(sr) == ""` 单独判断——`strings.Split(strings.TrimSpace(sr), "\n")` 对空字符串会返回长度为 1 的切片（`[""]`），空字符串交给 `url.Parse` 会得到一个空 `Scheme`，配合下面新增的按类型 scheme 校验其实也会被拦下，但报出的错误是"scheme 不匹配"而不是"输出为空"，容易误导排查方向；单独判断给出更准确的错误信息，不是为了补一个校验漏洞。非空时才按行分割。
  - 每行 URI 的 scheme 必须匹配**对应节点**的类型（`hysteria2`→`hysteria2`，`vless-reality`→`vless`），不再无条件要求 `hysteria2`；这依赖 §6.2 定下的"每节点恰好一行、顺序与输入一致"契约，按 `ns[i]` 对应第 `i` 行。
  - 新增校验：`len(lines) == len(ns)`，行数与已启用节点数不一致时报错（现状未检查这一点）。

## 9. Shell 兼容边界

### 9.1 共享检测：sectioned 格式探测

在 `install-proxy.sh` 中新增一个小函数，插入位置在 `validate_node_fields`（约 `:463` 附近）之后、`write_subscriptions_with_shell`（`:508`）之前，`cmd_install` 函数体内的两个调用点都在它之后：

```bash
nodes_conf_is_sectioned() {
  local file="$1"
  local line
  [[ -f "$file" ]] || return 1
  while IFS= read -r line || [[ -n "$line" ]]; do
    line="$(trim "$line")"
    [[ -z "$line" || "$line" == \#* ]] && continue
    [[ "$line" == \[*  ]] && return 0
    return 1
  done < "$file"
  return 1
}
```

判定规则与 `internal/nodes.detectFormat` 一致：第一条非空非注释行以 `[` 开头即认定为 sectioned。加 `[[ -f "$file" ]] || return 1` 是因为脚本开头 `set -euo pipefail`（`install-proxy.sh:2`）下，对不存在/不可读文件的 `< "$file"` 重定向会直接终止整个安装脚本，而不是让函数返回 1——必须在读之前显式挡住。

### 9.2 installer 自身节点写入（`install-proxy.sh:1072-1118` 附近）

**检测必须放在 `grep -q "# managed-by: installer"`（现有 `:1080`）判断之前，且无条件生效**——不能像最初方案那样放在 `grep` 判断内部：`nodes.Serialize` 不保留任何注释行，用户执行过一次 `node migrate`/`add`/`edit`/`enable` 等任意写操作后，`# managed-by: installer` 这行标记就已经被永久丢弃，导致检测代码进不了 `grep` 命中的分支、永远不会触发。正确结构：

```bash
if [[ ! -f "$NODES_CONF" ]]; then
  cat > "$NODES_CONF" <<EOF
# schema-version: 1
# managed-by: installer
$NODE_NAME|$PUBLIC_IP|$HY2_PORT|$PASSWORD|$OBFS_PASSWORD|$SNI
EOF
elif nodes_conf_is_sectioned "$NODES_CONF"; then
  log_warn "nodes.conf is in sectioned format; skipping automatic IP/port sync. Run 'proxyctl node add|edit $NODE_NAME --server $PUBLIC_IP --port $HY2_PORT --sni $SNI [--password ... --obfs-password ...]' manually (use 'add' if the node was removed after migration; include --password/--obfs-password if this install regenerated config.env)."
elif grep -q "# managed-by: installer" "$NODES_CONF"; then
  # ...现有 awk -F'|' 更新块，不变...
fi
```

即：文件不存在→按原逻辑首次写入 legacy 格式；已是 sectioned→无条件跳过并用 `log_warn` 告警，不管是否还带得住旧标记；仍是 legacy 且带标记→走原有 awk 更新。这与 v0.8"Shell 兜底保留旧模板并明确告警"（`plan.md:21`）是同一模式：检测 + 告警，不让 Shell 变"聪明"。

告警提示必须同时覆盖三种漂移，不能只提 IP/端口：(a) 节点若在 migrate 后被删除，`node edit` 会报 not found，提示需说明改用 `node add`；(b) 若本次安装因 `config.env` 丢失重新生成了 `PASSWORD`/`OBFS_PASSWORD`（`install-proxy.sh:900-912`）并据此重写了服务端配置，sectioned 分支不会同步这两个凭据到 `nodes.conf`，订阅会静默失效，提示里必须包含 `--password`/`--obfs-password`。

### 9.3 Shell 订阅渲染兜底（策略层拒绝，不是渲染器内部拒绝）

检测点放在 `run_proxyctl_merge`（`install-proxy.sh:746`）的 `else` 分支里，在调用 `write_subscriptions_with_shell` **之前**，不是塞进渲染函数内部：

```bash
run_proxyctl_merge() {
  local nodes_file="$1"
  local output_dir="$2"

  if [[ -n "$PROXYCTL_VALIDATED_BIN" && -x "$PROXYCTL_VALIDATED_BIN" ]]; then
    "$PROXYCTL_VALIDATED_BIN" merge --nodes "$nodes_file" --output "$output_dir"
  else
    if nodes_conf_is_sectioned "$nodes_file"; then
      die "nodes.conf is in sectioned format; the shell fallback renderer only supports legacy Hysteria2 format. Install a validated proxyctl binary and re-run merge."
    fi
    log_warn "Validated proxyctl unavailable; falling back to shell renderer (no service policy groups). Install proxyctl ${PROXYCTL_VERSION} and re-run merge to regenerate the full subscription."
    write_subscriptions_with_shell "$nodes_file" "$output_dir"
  fi
}
```

原因：决定"要不要降级到 Shell 渲染"本身就是这个函数的策略职责（v0.8 沿用的模式），`write_subscriptions_with_shell` 应该保持"我只会渲染 legacy"这一单一职责，不需要自己再判断该不该被调用。现状 `cmd_install` 主流程里这个 `else` 分支实际不可达（`install_proxyctl` 失败会在更早处 `die`），`merge-nodes.sh` 也没有 Shell 兜底路径（只调用 `proxyctl`），所以这条改动当前主要是防御性的，但两个函数的职责边界因此更清楚。

### 9.4 示例文件

`examples/nodes.conf.example` 每个现有 section 显式加一行 `TYPE=hysteria2`，体现新的写入约定。新增一个 `[JP-Reality]` 示例段，`UUID`/`PUBLIC_KEY`/`SHORT_ID` 沿用与 Hysteria2 一致的 `CHANGE_ME_*` 占位符风格（如 `UUID=CHANGE_ME_UUID`、`PUBLIC_KEY=CHANGE_ME_PUBLIC_KEY`）。因为 §3.3 已把 CHANGE_ME 子串检查放在格式校验之前，这类占位符会先被 CHANGE_ME 分支命中，报出与 Hysteria2 一致的"replace placeholder secret"提示，不会先撞上 UUID 正则或 base64 解码报出"invalid uuid format"这类不知所云的错误——这正是提前决定检查顺序的意义所在，示例文件不需要为了绕开格式校验而改用格式合法的假值。
