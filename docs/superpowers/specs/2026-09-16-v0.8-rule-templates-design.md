## 1. 背景与目标

现有 `internal/render.Clash` 输出一段写死的配置：只有「节点选择」「自动选择」两组，所有代理规则都指向「节点选择」。用户实际使用中需要两类能力：

1. 按服务分流到独立组，在客户端里为 AI、流媒体等服务单独选择出口。
2. 节点故障时自动切换（fallback），而不仅是 url-test 测速。

本版本插队于多协议与多平台之前：改动集中在 `internal/render` 与订阅生成链路，不碰节点 schema、健康探测和安全边界。

## 2. 非目标

以下内容来自 `plan.md`「第三阶段」需求池，本版本明确不做：

- 自定义规则插入、按地区分组、负载均衡（load-balance）。
- 模板配置文件、组开关或任何新的用户配置文件（因此不改 v0.7 备份清单）。
- 远程规则集镜像、规则缓存、规则下载失败降级：rule-provider 继续由客户端直接从 GitHub raw 拉取。
- 订阅版本号、ETag/缓存头、订阅更新时间显示。
- `sr.txt`（Shadowrocket URI 列表，无组概念）。
- `nodes.ValidateName` 与节点 schema、`proxyctl node` 命令行为。
- `install-proxy.sh update` 流程（升级后不自动重新生成订阅）。
- Shell 兜底渲染器同步新模板。
- `Write` 的非原子写入（先写 `clash.yaml` 再写 `sr.txt`）维持现状。

### 3.3 保留名与节点冲突

保留名 = 14 个组名 + `DIRECT` + `REJECT`。

- **只检查启用节点**：订阅只渲染启用节点，禁用节点不出现在 `clash.yaml` 中，不会造成名称冲突。禁用节点改名为保留名不报错；启用它之后下一次 `merge` 才会失败。
- 匹配为完全相等（区分大小写，与 Mihomo 名称匹配一致）。节点名字符集 `[A-Za-z0-9._-]` 不含中文，实际可能冲突的是 `GitHub`、`Disney`、`TikTok`、`Telegram`、`Google`、`Bilibili`、`Apple`、`Microsoft`、`DIRECT`、`REJECT`。
- 冲突时：`render.Write` 在创建目录和写入任何文件之前返回错误；`proxyctl merge` 输出包含冲突节点名的错误并返回 1；输出目录中已有的 `clash.yaml`、`sr.txt` 保持原样（字节不变），输出目录不存在时不被创建。
- 不修改 `nodes.ValidateName`：改动它会让已含此类名称的 `nodes.conf` 在 `node list` 等命令上直接读取失败，超出本版本范围。

## 5. `proxyctl validate` 校验契约

`validate` 仍只校验本次渲染结果，读取的节点文件与现有行为一致。校验分两层：

**节点层**（输入为启用节点）：保留现有的占位符与必填字段检查；新增保留名冲突检查（第 3.3 节），失败时输出冲突节点名并返回 1。

**YAML 结构层**（输入为 `clash.yaml` 字符串，与渲染器解耦，可直接喂入手工构造的 YAML 做负向测试）。「组是否存在」一律依据输入 YAML 中实际的 `proxy-groups` 定义，不使用渲染器导出的组名或保留名表：

1. YAML 可解析。
2. 名称唯一：`proxies` 名称互不重复；`proxy-groups` 名称互不重复；代理名与组名不相交；两者都不得为 `DIRECT` 或 `REJECT`。
3. 成员引用（全部组，沿用现有校验并改为 YAML 实际定义）：每个组的每个成员必须属于「YAML 中定义的代理 ∪ YAML 中定义的组 ∪ {`DIRECT`, `REJECT`}」。
4. 规则目标：`MATCH` 规则取第 2 段，其余规则取第 3 段；目标必须属于「YAML 中定义的组 ∪ {`DIRECT`, `REJECT`}」。
5. RULE-SET 引用（沿用现有）：每条 `RULE-SET` 规则引用的名称必须在 `rule-providers` 中定义。
6. 无未引用 provider（新增）：每个 `rule-providers` 条目至少被一条 `RULE-SET` 规则引用。

`sr.txt` 的现有校验不变。现有 validate 测试断言不得删弱。

## 6. 各组件改动边界

### 6.1 `internal/render`

- 策略组、rule-providers 与规则由内部数据描述，渲染器据此生成对应段落；输出确定、可复现（同一输入逐字节相同）。
- `func Clash(ns []nodes.Node) string` 签名不变。
- 新增导出：保留名列表与启用节点冲突检查函数（精确签名由实施计划定义）。
- `Write` 在任何文件系统操作前调用冲突检查。
- `Shadowrocket` 与 `sr.txt` 输出不变。

### 6.2 `cmd/proxyctl`

- `merge`：冲突时输出错误并返回 1（经由 `render.Write` 的错误，现有错误处理路径）。
- `validate`：按第 5 节实现；YAML 结构层抽为接收字符串的函数。这是可测试性重构——第 5 节的负向场景无法由 `render.Clash` 的正常输出触发；行为等价由现有 validate 测试原样通过证明。

### 6.3 安装脚本与用户文档

- `install-proxy.sh`：`write_subscriptions_with_shell` 的模板内容不变；其完成日志与 `run_proxyctl_merge` 的降级日志改为明确告警「使用降级模板，不含服务策略组；获取 proxyctl 后重新生成订阅」。降级路径的触发条件不变。
- `install-proxy.sh`、`merge-nodes.sh` 的 `PROXYCTL_VERSION` 默认值改为 `v0.8.0`，`tests/test_install_monitor.sh` 的固定版本断言同步。
- README：
  - FlClash 使用说明与「配置默认包含」列出 14 组、各组默认出口，以及「服务组可在客户端单独切换」。
  - 节点命名说明保留名冲突会导致 `merge` 失败。
  - 升级说明必须准确，不得笼统写「升级后跑一次 merge」。`install-proxy.sh update` 只升级二进制，不重新生成订阅；升级到 v0.8.0 后按以下任一方式重新生成：
    - 下载 v0.8.0 tag 下的 `merge-nodes.sh`（URL 固定到 `v0.8.0` 而非 `main`），再执行 `sudo ./merge-nodes.sh`。
    - 直接执行 `sudo /usr/local/bin/proxyctl merge --nodes /etc/singbox-sub-manager/nodes.conf --output "/var/www/proxy-sub/$(sudo cat /var/lib/singbox-sub-manager/token)"`。已有订阅文件被原地覆盖，保留原属主与权限。
  - 明确警告：旧版 `merge-nodes.sh` 内置 `PROXYCTL_VERSION=v0.7.1`，发现本机二进制版本不同时会下载 v0.7.1 并覆盖 `/usr/local/bin/proxyctl`，导致降级且订阅仍为旧模板。
  - 修正 README 中「要求已发布 `v0.6.0` Release」的过时表述。

不适用：渲染为纯函数；`Write` 与 `merge` 的文件 I/O 为本地同步调用，无 context、goroutine、channel、锁或网络调用，与 v0.7.1 相同。

## 8. 交付与 Task 划分

- 业务风险：中央 L1。普通功能；服务端不新增外部请求，不涉及认证、密钥或信任边界变化；客户端拉取规则集的信任模型与 v0.7.1 相同。非平凡改动，每个 Task 独立终审。
- 流程复杂度：中等，涉及 Go 渲染器、CLI 校验、安装脚本日志与用户文档，2 个 Task 顺序依赖。
- 分支：`feature/v0.8.0`（基线 `main` 的 `5e26383`）；设计、计划与实现在同一分支，一个 PR 合并。推送、PR、合并、tag 与 Release 均需另行明确授权。

每个 Task 按 `docs/agent-workflows/task-lifecycle.md` 的执行顺序独立完成审查、专项门禁、适用文档更新、主提交与状态封账提交，封账前不进入下一 Task：

| Task | 范围 | 适用用户文档（进入该 Task 主提交） |
|---|---|---|
| 1 | 渲染模板（第 3、4 节）、保留名冲突与 `Write` 前置检查、`validate` 校验契约（第 5 节）；测试 R1–R11、C1–C11 | README：FlClash 使用说明与「配置默认包含」、节点保留名说明；README 无 `validate` 章节，校验契约变化不另写用户文档，计划记录审计依据 |
| 2 | Shell 降级告警、`PROXYCTL_VERSION` 固定为 v0.8.0、Shell 测试 | README：升级与订阅重新生成说明、旧脚本降级警告、过时 v0.6.0 表述 |

渲染器与校验器必须在同一 Task 内交付：v0.7.1 的 `validate` 把合法成员写死为 `自动选择`、`节点选择` 与 `proxies`，渲染器单独加入 `故障转移` 等组后，正常输出的 `validate` 会报告未知成员，现有 `TestRunMergeAndValidate` 失败，Task 无法独立通过完整验证并封账。Task 1 的专项门禁须包含 `go test -race -count=1 ./...` 全量通过，不得跳过、延后或放宽任何现有测试。Task 2 不修改 Go 代码，依赖 Task 1 已封账。

各 Task 的状态封账提交同步更新实施计划的完成记录与 `plan.md`「当前实施基线」中 v0.8 行的状态。
