# 审查闭环

## 发现分类

审查结论必须标记为以下一种，避免责任和修复范围漂移：

- 原规格未实现。
- 原规格存在歧义或缺口。
- 实施缺陷。
- 修复引入的回归。
- 测试或门禁缺口。
- 文档与实际行为不一致。

## 每条发现的闭环证据

1. 给出可复现条件、实际行为、预期行为和代码位置。
2. 建立修复前会失败的确定性测试或最小命令复现。
3. 只修改根因，不按反馈关键词堆叠补丁。
4. 用同一测试证明修复后通过。
5. 检查相邻边界：成功、失败、取消、超时、状态持久化、资源释放和回滚中适用的部分。

若修复引入或替换 context、锁、trap、临时文件、状态字段、CI 步骤或工具版本，必须检查原有生命周期是否被覆盖。例如新增 EXIT trap 时检查已有 trap，新增子超时时检查 hook 在超时后返回成功值的路径。

## 审查轮次规则

- 后续复审使用上一次已审查提交作为基线，只检查未闭环项、本轮差异和明确回归，不重复全仓扫描。
- 有效 P1/阻塞问题未修复时不得合并或进入下一 Task。
- 测试通过但规格仍不满足时，结论必须写“门禁通过但规格未闭环”。
- Agent 的完成报告不作为证据；必须核对 Git 差异和新鲜命令输出。
