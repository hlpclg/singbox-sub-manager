# Task 生命周期

## 开始前

1. 记录分支、HEAD、工作区状态和用户已有修改。
2. 确认当前 Task 没有覆盖计划全局约束。
3. 使用验收矩阵把关键不变量映射到成功、失败、取消、超时和持久化测试；不适用项写明原因。
4. 明确本 Task 的文件范围、专项门禁和 README 适用性。

## 执行顺序

```text
契约确认
→ 验收矩阵
→ 最小实施
→ 聚焦测试
→ 规格符合性审查
→ 代码质量审查
→ Task 专项门禁
→ 计划与用户文档更新
→ 主提交
→ 状态封账提交
→ 下一 Task
```

不得积攒多个 Task 后统一审查。开发循环只运行聚焦测试；专项门禁在 Task 交接前最多运行一次。

## 文档状态

每个 Task 完成时必须在实施计划记录：

- 实际完成范围和偏差。
- 新鲜验证命令与结果。
- 主提交 SHA。
- README 或对应用户文档的更新情况。

改变命令、配置、安装、运维、兼容性或其他用户可见行为时，README 或对应用户文档必须进入主提交。纯内部实现、重构、测试或 Agent 工作流 Task可以不改 README，但计划必须记录“不适用”及原因。

Git 提交不能在自身内容中记录自身 SHA，因此使用两步封账：先创建包含实现和适用用户文档的主提交，再立即回填 SHA、验证证据和 Task 状态，以独立状态提交封账。封账前不得进入下一 Task。

## 完成检查

- 验收矩阵所有适用项已有证据。
- 未削弱或绕过既有测试和门禁。
- 暂存文件只包含当前 Task 范围。
- 计划状态、README 结论和主提交 SHA 已回填。
- 状态封账后工作区符合根 `AGENTS.md` 的洁净要求。
